# 机械臂还原：下一轮工作单

目标：同一姿势、同一分辨率下，桌面版臂杆的轮廓、销轴与壳体的比例、遮挡顺序、弯折节奏与原版逐项对齐。判定标准不是"看起来像"，而是下面每一项都能在代码里对上数、在渲染里量出来。

本轮只做静态核对：读了本地 `Assembly-CSharp.dll`（v1.11.8）、`OracleArm` / `OracleGraphics` 反编译、当前 `OracleArm*.cs` 与 `MainScene.unity`，未改代码、未构建。

## 先纠正上一轮审计里的两个数

1. `Joint.ElbowPos` 只有两种分法，不是"有限制时才 2:1"：
   - `next != null`（第 1–3 节）：`InverseKinematic(Tip, jointPos, L/3, 2L/3, ±1)`
   - 末节（第 4 节）：`InverseKinematic(Tip, jointPos, L/3, L/3, ±1)`，两段各 10 px，**总长只用到 20 px**，剩下 10 px 是余量。
   所以末节的肘点与我们的 15/15 差得最远，前三节其实一致。
2. "圆销标称 12 px"指的是第 1 节的**肘销**（`(6 - 0)/10 * 20 = 12`）。枢轴销是 `(7 - 0)/10 * 20 = 14`，与当地壳宽 15.4 px 基本等宽。桌面版枢轴销 18.9 px、肘销 16.2 px，是"游戏像素 × 1.35"的结果，而壳体用的是手写的 `rootThickness = 0.184`（18.4 px，原版同位置 15.4 px）。**销偏大是真的，根因是销乘了 `detailScale` 而壳没有，两者不是同一套像素账。**

## 统一契约：一切从"游戏像素"算，只有一个比例

- 现在相机 `orthographic size = 3.9`，1440p 下 1 世界单位 = 184.6 屏幕像素；贴图 PPU = 100，所以 **1 游戏像素 = 0.01 世界单位 = 1.85 屏幕像素**，这个换算已经是对的，不用改。
- 问题出在几何参数：`rootThickness / tipThickness` 是手写的，销轴与撑杆又各乘 `detailScale = 1.35`。下一轮删掉这三处自由参数，全部改成原版像素公式：
  - 壳体半宽 = `num3 * num5(t)`，`num3 = {7, 5, 4, 3}`（按节索引），`num5` 见下；
  - 枢轴销直径 14 / 肘销 12 / 齿轮 5×18 / 撑条 4×25×2 / 金属杆 1×L、1×(L+10)，全部按原值换算；
  - 底座三层板 30/17/20、24/15/30、30/17/20 也按原值。
- 收益：销与壳的比例由构造保证，不再需要"整体缩放对齐"，也就不存在缩小后其余细节跑偏的问题。

## P0 壳体几何（最影响近景观感，先做）

现状问题：每节固定 20 段、肘点两侧各裁掉 10% 曲线参数、单条带 + 顶点渐变，没有独立高光带。

原版（`OracleGraphics.ArmJointGraphics.DrawSprites`）：

- 每节两半，各画一条三次贝塞尔：起点 `joint`，控制点 `cA = joint + d*(dist*0.2)`、`cB = elbow - dirMid*(dist*0.2)`，终点 `elbow`；第二半同理从 `elbow` 到 `next`，两端共享 `dirMid`。
- 采样行数 = `meshSegs = totalLength / 10` → 30 / 15 / 9 / 3，**每行 4 个顶点**，不是一条四顶点带。
- 宽度轮廓：
  `num5(t) = 0.6 + 0.5*(1 - sin(πt)) + 0.3*max(sin(lerp(0,0.3,t)*π), sin(lerp(0.7,1,t)*π))`，`t == 1` 时强制 `0.5`。
- 侧移：`(k==0 && t>0.75) || (k==1 && t<0.25)` 时 `num5 *= 0.5`，`num6 = num5 * num3 * (index%2==0 ? 1 : -1)`；当地半宽就是 `num3*num5`，侧移量等于当地半宽——这就是钩肩的形状来源。
- 每行写入顺序：先"连接四边形"（用上一行中点到本行中点，宽度 `num3*(num5+num2)/2`），再"本行环"（宽度 `num3*num5`，位置 `center ± perpendicular(vertexDir)*num3*num5`，中心偏移 `num6`）。
- 高光层是**独立网格**：同一组行、同心、宽度和偏移都 ×0.5，颜色 `HighLightColor`；壳体 `BaseColor`。不是顶点渐变。

改动点：`OracleArmGraphics.cs` 的 `DrawRootShell / DrawShortShell / DrawCubicShell / AddShellRow` 整段替换为上表算法；删掉 `cut`、`ShellBands`、`LightDirection`。两半都不再裁 10%，曲线画到肘点，接缝由"肘销在壳后"决定露出多少。

### 实测：两条宽度曲线差在哪（第 1 节，`num3 = 7`）

按两边的公式直接算，单位是游戏像素（桌面版取值 `rootThickness = 0.184`）：

| t | 原版壳宽 | 桌面版壳宽 | 桌面/原版 |
| --- | --- | --- | --- |
| 0.00 | 18.8 | 14.7 | 0.78 |
| 0.10 | 16.4 | 18.7 | 1.14 |
| 0.25 | 13.2 | 13.0 | 0.99 |
| 0.50 | 10.3 | 9.6 | 0.93 |
| 0.75 | 13.2 | 11.7 | 0.89 |
| 0.90 | 16.4 | 17.6 | 1.07 |
| 1.00 | 7.0 | 13.3 | **1.90** |

两个结论：

1. 桌面版在中段与钩肩（0.25–0.75）基本吻合，误差 ≤11%，说明整体粗细并不是主要问题。
2. 肘端完全不对：原版在 `t = 1` 收紧到 7 px（`num5` 强制 0.5），桌面版还有 13.3 px。加上两侧各裁 10% 曲线，肘点附近根本没有"细腰"，肘销自然显小、钩肩不显眼。

销轴相对当地壳宽的实测：枢轴销 原版 14/16.4 = 0.85、桌面 18.9/18.7 = 1.01；肘销 原版 12/7 = 1.71、桌面 16.2/13.3 = 1.22。也就是说枢轴销偏大 19%，肘销反而"陷进"壳里 29%——两个方向的错。修完 P0 的壳宽曲线，肘销露出量会自动回到 1.71，不需要单独放大。

## P1 销轴、齿轮、层级（与 P0 同批）

- 尺寸：`pivotDisc = 14 px`、`elbowDisc = 12/9/6/3 px`（按节索引 `(6-index*1.5)/10*20`）、螺栓 `deerEyeB` 原尺寸 5 px、齿轮 `5×18 / 4.5×16 / 4×14 / 3.5×12`。全部去掉 `detailScale` 与 `bearingScale`。
- 位置：枢轴销在 `joint + dirToElbow * (index==0 ? 12 : 2)`，肘销正好在 `elbow`；`deerEyeB` 叠在两者之上。
- 层级按原版精灵索引顺序：齿轮(0-2) → 金属件(3-6) → 肘销(7-8) → 壳体(9-12) → 枢轴销(13-14)。桌面版当前是 `rod -14 / cog -13 / elbow -12 / shell -10 / pivot -8`，与之一致，**但壳层改成双网格后高光层要插在壳体与枢轴销之间**。
- 验收：截图量取第 1 节枢轴销直径 ÷ 当地壳宽 = 14/16.4 ≈ 0.85（现状 1.01），肘销 ÷ 壳端宽 = 12/7 ≈ 1.71（现状 1.22）。

## P2 撑杆与金属件（去掉限长）

现版对两根杆都做了裁剪（近杆 ≤0.9 引导距离、远杆 ≤ 第二段长度），并把撑条缩短到 0.75。原版：

- 近杆：从肘点指向 80% 弦点，长度固定 `L/4`（不裁剪，允许穿出壳体）；
- 远杆：从 `next` 指向近杆端点，长度 `dist + 10 px`（同样不裁剪）；
- 撑条：`MirosLegSmallPart`，`scaleX = 1.5/1/0.8 × ±1`、`scaleY = 2/1/0.5`；
- 齿轮转速 `cogRotat += (lastChord - chord)/L * ±2`（这个已经对）。
- 验收：静止姿势下近杆末端应超出现有壳端约 10 px，远杆末端那颗 `deerEyeB` 出现在壳外——这是原版可见的"轴端露头"。

## P3 运动学（决定折叠顺序与节奏）

外观对齐后，姿势仍会不同，因为求解器不同。原版：

- `Joint.Update`：`vel *= 0.8`（MSC 0.7），逐关节积分；index 0 钉在底座；index 1 在底座移动或肘点落在实心格时，用两次 `InverseKinematic` 比较翻转侧，选碰撞少的一侧；
- 距离约束：`num4` 权重（index 0 → 0，倒数第二节 → 1，其余 0.5）；`num6 = LerpMap(前后杆点积, -1..1 → 1..0.2)`，即夹角越大允许缩得越多，最近可到 20%；
- 末节：锚到 `bodyChunks[1] + 沿 GetToDir 的 L/2 偏移`，再把自己拉到距 `bodyChunks[0]` 正好 `totalLength` 的位置（当前桌面版锚在背部挂点，且用 30 单位长度）。
- 桌面版：FABRIK 两端迭代 + 统一 74%–100% 缩放 + 重力。

建议分两步：P3a 只把**长度与肘点**改成原版（末节 1/3+1/3、允许 20% 折叠、末节锚到躯干上块），保持现有求解器；P3b 若要完全一致，再把逐关节积分与 index 1 的翻转逻辑移植过来。P3a 不改手感结构，风险低，先做。

## P4 验收方法（写死，避免"看起来像"）

1. 固定姿势矩阵：静置、右侧、右下角、快速拖拽中、松手 0.5 s。用 `-previewCapture -previewDelay` 抓帧，1440p。
2. 每次改动都量三个数：枢轴销/壳宽、肘销/壳宽、钩肩出现的 t；数值对不上就不算完成。
3. 叠图：把原版同姿势帧（本地录像或游戏内截图）与桌面帧按"人偶头宽"归一化后叠在一起，检查壳端到肘点的距离与销心位置。
4. 构建按仓库约定：临时目录出包核对，成功后再替换 `Iterator_Build`，只留这一个可运行构建。

## 参考素材复核（2026-11-25，子任务索引）

`Random Gods.mp4`（Wallpaper Engine 创意工坊 3024177030，1920×1080/30fps/37:58）经抽帧核对，**是同人壁纸重绘，不是原生画面**：

- 机械臂被画成光滑灰管，没有可分辨的枢轴销盘与轴心孔；肘部 12× 放大是圆角矩形；底座枢轴位置只有两个圆角凸起。
- 整体压暗红紫、有柔光低通（边缘 3–4 px 渐变），颜色不能当材质参考；画面还叠了红色螺旋装饰线，与主缆视觉重叠。
- 构图固定：人偶质心全程 ±2 px、底座 x 恒 947–950，**没有任何滑动/过角镜头**。
- 可量到的只有"等效直径"：杆身近底座 20.5–27 px、中段 11.5 px、肘部 14.1 px、第 2 关节 22.1 px、腕球 14.1 px（±3 px）。

对 P0 的意义：

- 它的**杆身中段/根部比 11.5 / 21 ≈ 0.55**，与桌面版 `num5` 轮廓给出的 10.3 / 18.8 ≈ 0.55 一致——说明轮廓曲线的形状是对的。
- 它的**杆宽/头宽 ≈ 21 / 16 ≈ 1.3**，与游戏公式的 18.8 / 11 ≈ 1.7 不符；差异来自重绘，不能用来改公式。
- 现有原生截图 `Builds/RefPuppet/reference.png` 也无法标定比例：浅色臂身 33–40 px、粉色头部约 48 px，对应 2×–4× 的未知放大，缺少拍摄参数就不能当像素尺。

结论：像素级验收仍以反编译公式为准；素材只能裁决"大轮廓、遮挡、是否存在"。要满足仓库的验收条款（静置→移到侧边→停稳→拖拽→松手），仍需一段原生、未缩放、连续动作的录像。
